今日学习计划

今天这篇是 `Tool Use` 的下半场。上一篇《Agent Day2：`Tool Use` 学习（上）——调用流程、幂等、错误处理与 `Tool Registry` 四域架构》把"模型说要调"和"调完怎么回填"讲完了，今天往前再走一步，盯四件更靠近运行时的事：**`Tool Runtime`、`MCP`、安全，以及评测**。

为什么把这四个放一起？因为它们是同一条链上的：模型给出意图后，**真正的执行发生在你的代码里**，这层就是 `Tool Runtime`；工具越来越多、要给不同宿主复用时，需要 `MCP` 把能力标准化；跑起来之后，鉴权和隔离决定它会不会闯祸；而最后，你拿什么证明这一切"真的变好了"——那是评测。

今天的学习目标，我用四个问题来组织：

1. 一次工具调用，从进入到返回，执行层到底要过几道关？（`Tool Runtime`）
2. `MCP` 到底解决了什么，三个角色和三类能力分别是什么？
3. 工具调用的安全边界在哪——凭什么信一次调用？
4. 用什么指标和实验，证明"改完真的有效"？

涉及的单词我都用反引号标出来了，方便回头查。下面开始。

## 一、`Tool Runtime`：让一次调用可观测、可控制、可追责

上一篇讲的 `Tool Registry` 是工具的"声明"，但声明只是一份契约。真正把一次调用落到结果上的，是执行层。我的理解是：**`Tool Runtime` 的职责，是把一次调用变成一次可观测、可控制、可追责的操作。**

在我做的标书 Agent 里，工具治理就是靠 `Tool Registry` + `Tool Runtime` 统一管 schema、参数校验、超时重试、幂等与审计；工具按注册发现、按会话动态启用，并发调用不串号，新增工具只注册、不改主流程。

一次调用进来，执行层按固定顺序过七道关（顺序基本不能换）：

```
1. 白名单校验 —— 这个 Agent 能调这个工具吗
2. 参数校验   —— JSON Schema + 业务规则，两层
3. 鉴权       —— 租户 / 角色 / 数据范围
4. 幂等检查   —— 幂等键是否已执行
5. 执行       —— 超时 / 重试 / 限流 / 熔断
6. 结果裁剪   —— 截断 / 结构化 / 脱敏
7. 审计       —— 输入输出、耗时、token
```

这张链路图建议默画一遍。面试也好、自己 review 也好，问到"工具调用怎么做的"，画完这条就赢一半。落到代码里，关键就是那几个判断：

```java
public ToolResult invoke(ToolCall call, AgentContext ctx) {
    ToolSpec spec = registry.get(call.name())
            .orElseThrow(() -> new UnknownToolException(call.name()));
    if (!ctx.allowedTools().contains(spec.name())) return ToolResult.denied("工具未授权");
    Args args = validator.validate(call.arguments(), spec.inputSchema());
    authz.check(ctx.tenantId(), ctx.userId(), spec.requiredScopes());
    String key = spec.idem() == KEY_REQUIRED ? idemKey(ctx.taskId(), spec.name(), args) : null;
    if (key != null && idemRepo.exists(key)) return idemRepo.get(key);
    long t0 = System.nanoTime();
    ToolResult r;
    try {
        r = limiter.execute(spec.name(), () -> retryTemplate.execute(c -> executor.call(spec, args)));
    } catch (TimeoutException e) {
        r = ToolResult.retryable("工具超时: " + spec.name());
    }
    r = trimmer.trim(r, spec.outputSchema(), MAX_RESULT_TOKENS);
    audit.log(ctx.traceId(), spec.name(), args, r, elapsed(t0));
    if (key != null) idemRepo.save(key, r);
    return r;
}
```

几个我踩过坑的点：

**参数校验必须两层。** `schema` 管类型，业务规则管语义。只看 `schema`，把 `"30"` 当日期传进去，下游直接炸。

**结果裁剪最容易被忽略。** 一个订单查询返回 200 条 `JSON`，直接回填就把上下文撑爆了，后续推理全乱。我的裁法有三种：列表类**截断**（留前 N 条 + "还有 X 条"）、结构化数据**字段裁剪**（只留模型需要的）、长文本**摘要**（用小模型先总结）。原则是——**回填给模型的是它做判断需要的最小集，不是原始数据**。

**错误要分类，别一律重试。** `401` 重试三次，既费钱又放大故障。我的分类是：瞬时错误（`timeout`、`429`、`502`）退避重试；永久错误（`401`、`404`、参数非法）立即失败；参数错了把**可执行的错误信息**回填给模型让它重生成（最多两次）；权限或业务规则拒绝的，中断上报走 `HITL`。

给我印象最深的是错误信息怎么写。差的是 `{"error": "Invalid argument"}`，好的是 `{"error": "字段 from 格式错误：期望 YYYY-MM-DD，收到 '2026/1/1'。请用 2026-01-01 重试。"}`——**回填给模型的错误，必须是它能照着改的**。

## 二、`MCP`：把 M×N 变成 M+N

工具多了之后有个很现实的问题：M 个模型 × N 个工具，就是 M×N 套适配。`MCP`（`Model Context Protocol`）解决的就是这个组合爆炸——有了它变成 M+N。

三个角色要先分清：

| 角色 | 是谁 | 职责 |
|---|---|---|
| `Host` | 宿主应用（Claude Desktop、你的 Agent 平台、IDE） | 管理连接、决定暴露哪些能力、做权限与确认 |
| `Client` | `Host` 内部的连接器 | 与某个 `Server` 一对一通信 |
| `Server` | 能力提供方（你的业务系统） | 暴露 tools / resources / prompts |

三类能力，我用一个记忆法：**`Tools` 是"做"，`Resources` 是"看"，`Prompts` 是"问的模板"。** `create_ticket` 这种有副作用的是 `Tools`；`file:///docs/spec.md` 这种只读的是 `Resources`；`/summarize` 这种预置模板是 `Prompts`。

传输上，`stdio` 最简单（`Host` 拉起 `Server` 子进程）；远程场景旧的 `HTTP + SSE` 正在被新的 `Streamable HTTP` 逐步替代。生命周期是 `initialize`（交换协议版本与 capability）→ `initialized` 通知 → 正常调用 → 关闭。**能力协商是关键**——双方各自声明支持什么，不支持的不能假定存在。

我在 ASC 里做过一个 `MCP Server`（11 个工具），架构上就是把 `Registry` 里的工具批量适配成 `MCP` 的 tools 列表，额外暴露 resources（状态卡）和 prompts（分析模板）。做过之后才发现，"读过文档"和"真的做过"的分界线在四个治理点：

1. **工具描述要写"何时不用"**，否则模型乱调——写"什么时候不该用"，比写"这个工具做什么"更能降误用率。
2. **`Server` 侧必须自己做鉴权**，`Host` 传过来的身份不能盲信。
3. **返回体积要控**——`MCP` 没有强制大小限制，一个 resource 返回 5MB 会直接打死上下文。
4. **版本与能力协商**——升级协议版本要兼容旧 client，否则用户端集体连不上。

## 三、安全：凭什么信一次调用

工具调用的安全，本质上是在回答一句话：**凭什么相信这一次调用是合法的、且不会越界。**

我的做法分几层：

**入口层——白名单与鉴权。** 每个 `AgentContext` 明确它能调哪些工具（`allowedTools`），不在名单里直接拒绝。鉴权看三样：租户 `tenantId`、用户 `userId`、所需权限 `requiredScopes`。

**身份层——不盲信上游。** 这一点在 `MCP` 场景尤其重要：`Server` 侧要独立校验 token 与租户，不能因为调用来自 `Host` 就放行。项目里我用的是 `JWT` + `RBAC`。

**隔离层——多租户统一 404。** 跨租户访问统一返回 `404` 而不是 `403`，防止探测——**通过响应差异泄露资源是否存在，本身就是一种漏洞**。

**结果层——脱敏。** 审计日志和回填给模型的结果都要脱敏，敏感字段不进上下文。

**副作用层——幂等。** 上一篇讲过，所有 `sideEffect == true` 的工具强制幂等键，key 用 `hash(taskId + toolName + canonicalJson(arguments))`。安全角度它还有一层意义：**防止一次故障被重试放大成多次副作用**。

## 四、评估：凭什么说"改完真的有效"

这是最容易被跳过、却最能体现工程成熟度的一环。一句"感觉变好了"在工程上等于没说。

先说一个反直觉的判断：**想测工具调用方案，得先把模型的随机性按住。** 真实模型不可复现——同样输入两次结果不同，你改了 A 分数变了，分不清是 A 的功劳还是随机波动。所以我用 `MockAgent`（规则决策器）替代真实模型做确定性仿真，让两次运行唯一的差异只剩"注入了什么上下文"。

评测工具调用，我会盯这几个指标：

| 指标 | 回答什么问题 |
|---|---|
| **工具选择准确率** | 固定 50 条 query，改描述前后各跑一遍对比——不靠感觉 |
| **重复调用率** | 相同 `(tool, args)` 重复出现的次数 / 总调用数，哈希去重 |
| **约束违反率** | 规则守住了吗 |
| **任务完成率** | 活干完了吗 |
| **输入 token** | 一次调用注入的上下文成本 |

怎么保证结论可信？三条：

**第一，单变量。** 模型版本写死（不用 `latest`）、温度 0、同一批样本、同一个判分器。换模型顺便换提示词，就永远无法归因。

**第二，加对照。** 除了 baseline，我加了一组"无限窗口"对照，结果 token 仍从 147 降到 47（−68%），这就排除了"只是截断了历史"这个解释。

**第三，报方差。** 每场景 `N ≥ 5`，报均值和方差，不报单次。20 条样本上的 5% 差异，大概率是噪声。

我在 ASC 上的一组数字（口径：**确定性仿真，隔离模型变量**）：每轮输入 token **161 → 47（−70.8%）**，关键约束违反率 **33.3% → 0**，重复工具调用 **3 → 0**，恢复步数 **2 → 1**，两组任务完成率都是 **100%**。

这里要特意提示一句：**"完成率持平"这一条最重要。** 省 token 最容易的做法是少给信息，但那会掉正确率。完成率不变 + token 大降，才证明是"提效"而不是"偷工减料"。

边界也得说清：**这些都是注入层/仿真的结果，不是端到端收益。** 仿真只是下限验证——它能证明机制在原理上有效，不能证明在真实模型上也有效。真实 `LLM` 端到端评测我的 v0.7 还在做（同模型、温度 0、结构化决策输出、规则化判分、每场景 `N ≥ 5`）。**主动承认边界，比声称"我验证过了"可信得多。**

## 小结

今天这四个点，其实是一条线：

- **`Tool Runtime`** 让执行可控——七道关，顺序不能乱；
- **`MCP`** 让能力可复用——把 M×N 变成 M+N，但鉴权和体积还得自己做；
- **安全**让调用可信——白名单、独立鉴权、租户隔离、脱敏、幂等；
- **评测**让改进可证——单变量、加对照、报方差，完成率持平才算真提效。

一句话收束：**控制权要在代码里，不在模型里；不能评测的优化都是猜测。**

这套东西在你那儿大概率不成立的地方是 X——比如你的工具就三五个、根本没有复用和租户问题，那 `MCP` 和整套治理层就是纯开销。欢迎说说你的场景。
