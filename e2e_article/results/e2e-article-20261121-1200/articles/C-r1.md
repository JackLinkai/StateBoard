今日学习计划：接着上一篇《Agent Day2：Tool Use 学习（上）》往下写。上一篇我把调用链路、`幂等`、`错误分类`和 `Tool Registry` 的四域架构过了一遍，算是回答了"模型吐出一个意图之后，工具怎么被登记、怎么不出乱子"。但留言里被问得最多的，反倒是执行那层到底长什么样、工具要开放给别的系统该怎么定协议、怎么防住越权，以及"你说变好了，凭什么"。今天这四节就依次回答：**`Tool Runtime`、`MCP`、安全、评估**。我当时给自己定的目标是：读完你能默画出执行层的那几道闸门，讲清 `MCP` 的三个角色和三类能力，指认出返回体积这个最容易被忘的坑，并且能拿一组带口径的数字去回答"到底有没有变好"。

## Tool Runtime

上一篇讲的是"工具怎么被声明和登记"，这一节讲的是"真正干活的那层怎么设计才敢碰生产数据"。我给它的定义就一句：把一次调用变成一次**可观测、可控制、可追责**的操作。

我最早写的执行层很朴素：拿到工具名，查注册表，调函数，把结果塞回消息。跑通原型之后，我就觉得这层没什么可写的了。真上了两个公司级项目才发现问题全在细节里——有一次一个查询工具返回了几百条记录，我原样回填给模型，接下来几轮推理全乱了，模型开始答非所问。我当时想的是"模型不行"，换了更强的模型，照样乱。后来才定位到：不是模型的问题，是我把一堆它根本用不上的数据灌进了它的工作台。

现在这一层我会固定走七道闸门：**`白名单` → `参数校验` → `鉴权` → `幂等检查` → `执行` → `结果裁剪` → `审计`**。顺序不是随便排的：先问"这个 Agent 有没有资格调这个工具"（白名单），再校验参数的类型和语义，然后做租户与数据范围的鉴权；`幂等` 这一步上一篇细讲过，这里只保留一次检查；真正执行时挂上超时、重试、限流；结果回填之前先裁剪；最后把输入、输出、耗时、`token` 全记进审计。

### 结果裁剪：最容易被忘了的一道闸门

七道里我最想单拎出来讲的就是结果裁剪。它不产生"对错"，但能直接决定后面几轮推理的质量。一个订单查询返回 200 条记录、每条十几个字段，原样回填会把上下文撑到模型看不清重点。

我试过的三种裁法各有各的用处：**列表类截断**，只留前若干条再补一句"还有 X 条"；**结构化数据按字段裁剪**，只留模型做判断真正需要的那几个字段；**长文本用小模型先摘要**再回填。原则始终是同一句——回填给模型的是它做判断所需的最小集，不是原始数据。

这一层的边界也得说清：它保证的是"调用可控、事后可查"，但不替你决定"该不该调这个工具"，那个判断在编排层；而且白名单、鉴权这些闸门的配置本身也要版本化，否则改一次配置就能把整条链改歪。

## MCP

如果说 `Tool Runtime` 是"自己家里怎么把工具跑稳"，`MCP` 解决的就是"工具怎么卖给外面用"。它要解决的其实是组合爆炸：M 个模型 × N 个工具，各写一套适配就是 M×N 套；有了统一协议，变成 M+N 套。我现在那个状态治理项目对外暴露的 Server，最早是 11 个工具，后来端到端测试又补了 4 个，现在是 15 个——如果不是走协议而是逐个接，光适配就够喝一壶。

### 三个角色与三类能力

`MCP` 里只有三个角色：`Host` 是宿主应用，管连接、决定哪些能力暴露给模型、负责权限和确认；`Client` 是 Host 里的连接器，跟某一个 Server 一对一通信；`Server` 就是能力提供方，把 `Tools` / `Resources` / `Prompts` 暴露出来。三类能力也很好记：**`Tools` 是"做"**，有副作用、由模型决定调用；**`Resources` 是"看"**，只读数据、由应用或用户挂载；**`Prompts` 是"问的模板"**，用户显式选。我当时就是靠"做 / 看 / 模板"这三个字才没把它们搞混。

传输上，本地进程用 `stdio` 最简单；远程从老的 HTTP + SSE 在往 `Streamable HTTP` 迁。还有一条容易被跳过的是生命周期里的能力协商：`initialize` 阶段双方交换协议版本和支持的能力，不支持的不能假定存在。跳过这一步的后果我印象很深——升级协议那次，客户端集体连不上。

`MCP` 不解决鉴权和体积控制：协议把"工具是什么"标准化了，但"谁能调、返回多大"仍要 Server 自己扛。这是读过文档和真正做过 Server 的分界线。

## 安全

安全这一节我不想讲成清单，因为真正出事的往往不是"没想到要鉴权"，而是"以为别人替你鉴权了"。

最典型的一个错：Host 传过来的身份我直接信了。后来我把这条改掉——**`Server` 侧必须独立校验 `token` 和租户**，不能因为请求是从自家 Host 来的就放行。多租户场景里，跨租户一律按"不存在"处理，统一回一个 404，不给探测的口子。权限模型上用 `RBAC` 管角色、用 scope 收窄数据范围，工具声明里就带上所需 scope，执行层做鉴权时逐个比对。

还有一次我图省事，审计只记了工具名和返回结果，把输入参数略了。后来线上出问题要复盘，我根本还原不出模型当时看到的是什么——从那以后输入、输出、耗时、`token` 四样一样不落。审计不是给检查看的，是给未来的自己留案卷。

第二类坑是返回体积。`MCP` 没有强制的大小上限，一个 resource 返回几兆能把上下文直接打死，效果跟前面那"几百条记录"一模一样。所以这一节和 `Tool Runtime` 那节是呼应的：控体积不是单纯的性能优化，是一条安全约束。

第三类是版本协商。工具 schema 一改，老 Agent 可能直接崩。我的做法是 `name@version` 双写，旧版本保留一个发布周期再下掉；协议升级时兼容旧 Client，别让线上用户集体掉线。说白了，安全不只是"防坏人"，也包括"别让系统的变化把好人挡在门外"。

## 评估

这一节回答开头那个问题：你说改完变好了，凭什么。

我最早的做法是改一版、试三个 case、觉得好了就发。直到有人问我"到底提升了多少"，我答不上来——那几个 case 是我自己挑的，我甚至隐约知道怎么问才能让它答对。那一刻我才承认：**没有评测集的优化，本质是在用你的记忆做回归测试。** 那段时间我每周都在重复同一个动作：改一版、试几例、发一版、被打回来。最难受的不是改错，是改对了不知道对在哪、改错了要等下一周才暴露。

我现在的方法是三条。第一，**隔离变量**：用一个规则决策器替代真实模型做确定性仿真，这样两次运行唯一的差异只剩"注入了什么上下文"，因果链才清楚。第二，**固定一切**：模型版本锁死、`temperature` 固定为 0、同一批样本、同一个判分器，每个场景至少重复 5 次，报均值和方差，不报单次。第三，**加对照**：除了基线再加一组"无限窗口"上界，回答"离天花板还有多远"，顺便排除"只是截断了历史"这种解释。

### 用带口径的数字说话

拿我这边的两组结果说，口径我都标出来。状态治理那组在**确定性仿真、隔离模型变量**的条件下：每轮注入 `token` 从 161 降到 47（−70.8%），关键约束违反率从 33.3% 降到 0，重复工具调用从 3 次降到 0 次，跨会话恢复步数从 2 步降到 1 步，而两组任务完成率都是 100%——完成率持平这条最关键，它证明是提效，而不是靠少给信息偷工减料。上下文那组是**固定语料加哈希嵌入的确定性下限验证**：每查询注入 `token` 从 1002.8 降到 128.7（−87.2%），`recall@3` 保持 1.0 不降。

这些数字的口径必须一起讲：它们是注入层、下限验证的结果，不是端到端的承诺。真实模型下模型自己还会犯别的错，账不能全记在这一层。能主动把边界说出来，比声称"我验证过了"要可信得多。

### 边界：这套东西什么时候不成立

工具治理这一整套，也有它不灵的地方。工具数量很少、调用没有副作用、几轮就结束的任务，搭 `Tool Runtime` 和 `MCP` 基本是纯开销，有个 `Tool Registry` 加一层注册就够了。协议化只有在"同一个 Server 要给多个宿主复用"时才划算，单一应用直连接口反而简单。评测集如果一周不更新就会开始过拟合，给你假的好消息，得把真实的 bad case 持续回补进去。还有最容易被自欺的一条：指标多了以后，容易变成"为了分数好看而改方案"，这时候要回头看真实用户的问题。

下一篇我打算接着写写"评测集怎么进 CI、改一次跑一次"这件小事，它是把上面这套从"偶尔跑跑"变成"天天守着"的关键。

这套东西在你那儿大概率不成立的地方是工具数量和复用面，欢迎说说你的场景。
