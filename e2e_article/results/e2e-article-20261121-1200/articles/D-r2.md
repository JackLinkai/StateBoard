今日学习计划：把 `Tool Use` 的下半场补完。上一篇《Agent Day2：`Tool Use` 学习（上）》已经把调用流程、幂等、错误分类和 `Tool Registry` 四域架构讲透了，我当时想的是——真正决定它能不能上生产的，是剩下那几层：谁在执行、用什么协议接进来、谁有权限调、以及我凭什么说它变好了。今天这篇只谈四件事：`Tool Runtime`、`MCP`、安全、评估。涉及到的词我都用反引号标出来，重点结论用加粗标出。

# Tool Runtime

上一篇讲的是声明层——工具怎么描述、怎么注册。这一节讲的是执行层。我给它的定义只有一句：`Tool Runtime` 是把一次调用变成一个**可观测、可控制、可追责**的操作的那层代码。

## 我试过的错：把执行层当透传

最早我的实现特别简单：拿到 `tool_calls` 里的 `arguments`，解析之后直接调对应函数，把返回值塞回 `messages`，跑通一个 `demo` 就够了。

真正出问题是在上线之后。一个有副作用的工具因为网络抖动超时，上层重试，结果产生了重复写入。我当时想的是"限制重试次数就好了"，后来才想明白：根因不是重试，是**我没有把执行当成一个有状态的、需要被记录的操作**。没有记录，就没有"这次到底做没做过"的答案。

我后来给每次调用都留了一条贯穿全链路的痕迹：从调用发起、到工具执行、再到回填给模型，中间任何一步都能单独拿出来复盘。这一步做完，我第一次能回答"问题到底出在参数、权限，还是工具本身"。

第二件事是体积。一次订单查询返回 200 条 `JSON`（口径：单次查询的返回条数），我原样回填，下一轮 `Agent` 的推理直接乱掉。第三件事是追责：有人问我"当时传了什么参数、谁批准的、花了多久"，我一样都拿不出来。

> **执行层不是转发器，它是工具调用的闸门，也是黑匣子。**

## 最后的做法：一次调用七步

我把执行固化成七步，顺序不能换：

| 步 | 环节 | 我为什么把它放这儿 |
|---|---|---|
| 1 | `白名单` | 不在名单里的工具，参数都不用看 |
| 2 | `参数校验` | `JSON Schema` 管类型，业务规则管语义 |
| 3 | `鉴权` | 租户、角色、数据范围，无权限不该占幂等检查 |
| 4 | `幂等` | 有副作用的调用先查 `hash(taskId + toolName + canonicalJSON(args))` |
| 5 | `执行` | 超时、重试、限流、熔断都包在这一步里 |
| 6 | `结果裁剪` | 回填最小充分集，不是原始数据 |
| 7 | `审计` | 输入输出、耗时、`token` 全记下来 |

这七步的顺序我调整过一次。最早把 `结果裁剪` 放在 `审计` 之后，审计记下来的是没裁剪的原始返回，排查问题时又被这一大坨数据淹了一次；把顺序倒过来之后，审计记的就是真正回填给模型的内容，复盘才有了意义。

`白名单` 先于 `参数校验`，是为了让非法工具早点被挡掉；`鉴权` 先于 `幂等`，是为了不让没权限的调用占用幂等键。重试和错误分类上一篇已经讲过，这里不重复——`执行` 这一步只负责把它们包在同一层里。

`结果裁剪` 三种：`列表截断`（保留前 N 条加"还有 X 条"）、`字段裁剪`（只留模型做判断需要的字段）、`小模型摘要`（长文本先总结再回填）。原则是**回填的是最小充分集**。

> **可观测靠审计，可控制靠白名单与鉴权，可追责靠一次调用一条完整记录。**

# MCP

如果工具只在一个 `Agent` 里用，直连就够了。一旦要被多个宿主复用，问题就从"怎么调"变成"M 个模型 × N 个工具"的适配爆炸。

## 组合爆炸与三个角色、三类能力

`MCP`（`Model Context Protocol`）解决的是 **M×N → M+N**。它不是传输，是能力描述协议：把工具、数据、提示模板标准化之后，同一个 `Server` 能被不同 `Host` 复用，不用各写一套适配。

三个角色我按职责记：`Host` 管理连接、决定暴露什么能力、做权限与确认；`Client` 是 `Host` 内部的连接器，跟一个 `Server` 一对一；`Server` 是能力提供方，对外暴露 `tools` / `resources` / `prompts`。

这个拆分不是形式主义：`Client` 把协议细节挡在 `Host` 之外，`Host` 只需要决定"哪些能力可以暴露"，`Server` 只需要关心"我提供什么"。任何一边越界，复用就会退化成又一套私有适配。

三类能力更好记：`Tools` 是"做"（有副作用，模型决定调用），`Resources` 是"看"（只读数据，由应用或用户挂载），`Prompts` 是"问的模板"（用户显式选择）。我自己把它缩成一句：**做、看、问模板**。

我做的 `ASC` 现在对外是 15 个工具（口径：原版 11 个 + 端到端测试新增 4 个），做法就是把 `Registry` 里的工具批量适配成 `tools` 列表，再额外挂状态卡作 `resources`、常用分析模板作 `prompts`。

## 传输迁移与四个治理点

传输上，本地用 `stdio`（`Host` 拉起子进程，最简单）；远程我从 `HTTP` + `SSE` 迁到了 `Streamable HTTP`（请求响应 + 可选流式），`SSE` 是旧方案的单向流。

生命周期是 `initialize`（交换协议版本与 `capability`）→ `initialized` 通知 → 正常调用 → 关闭。**能力协商是关键**：双方各自声明支持什么，不支持的不能假定存在。

真正把"读过文档"和"做过"分开的，是四个治理点：

1. 工具描述写明"何时不用"，这条在 `Server` 侧要再落一遍。
2. `Server` 侧必须自己做鉴权，`Host` 传来的身份不能盲信。
3. 返回体积要控，`MCP` 没有强制大小上限，一个 `resource` 返回过大就会打死上下文。
4. 版本与能力协商：升级 `protocolVersion` 要兼容旧 `client`，用 `name@version` 双写，旧版本保留到客户端完成迁移。

> **协议解决复用，不解决信任和体积；那两件事仍然在你的 `Server` 里。**

# 安全

这一节不铺概念，只讲四个最容易出事的面。

## 鉴权、越权、返回体积与版本协商

**鉴权与越权。** `Host` 传来的 `token` 与租户身份不能盲信，`Server` 侧要独立校验。我早期把权限判断只放在 `Host`，结果任何能连上 `Server` 的调用方都能摸到内部工具——越权不是"模型乱调"，是**身份链路缺了一环**。后来我把 `requiredScopes` 校验下沉到 `Server`，又在 `Runtime` 的 `鉴权` 步里做租户与数据范围校验，`Host` 与 `Server` 各管一段。

**返回体积。** `MCP` 没有强制大小限制。我的做法是把裁剪收敛到 `Runtime` 的 `结果裁剪` 步：`列表截断`、`字段裁剪`、`小模型摘要` 三种裁法对 `tools` 和 `resources` 一视同仁。回填给模型的是最小充分集，不是原始数据。

**版本协商。** `initialize` 阶段交换 `protocolVersion` 与 `capability`，升级时兼容旧 `client`，`name@version` 双写。这一步不做，升级那天就是集体掉线。

> **安全不是加一道门禁，是把身份、体积、版本都收敛到同一层，让它可追责。**

# 评估

前面三节说的都是"我觉得这样更稳"，但**不能评测的优化都是猜测**。这一节讲我怎么把"感觉变好了"变成一个能复现的数。

我试过的错：改一版配置，手测几个 `case`，觉得好了；过两天又出错。问题在于那几个 `case` 是我自己挑的，我甚至隐约知道怎么问才能让它答对。**没有评测集的优化，本质是在用我的记忆做回归测试。**

最后的做法是对照实验守唯一变量：模型与版本写死、采样参数固定、提示词版本化、同一批样本、同一个判分器、同一套环境；设计上用 `A/B`、`A/B/C` 加消融，每场景重复 `N ≥ 5`（口径：每个场景的最少重复次数，报均值和方差，不报单次）。

最关键的一步是**确定性仿真**：用 `MockAgent` 规则决策器替代真实模型，让被测的只剩"注入了什么上下文"。模型是最大的噪音源，把它固定住，因果链才清晰。但这条一定要讲清边界：这只是**下限验证**，证明机制在原理上有效，不等于在真实模型上同样有效。

数字都带口径：

| 项目 | 指标 | 变化 | 口径 |
|---|---|---|---|
| `ASC` | 每轮输入 `token` | 161 → 47（降 70.8%） | 确定性仿真，规则决策器隔离模型变量 |
| `ASC` | 关键约束违反率 | 33.3% → 0 | 同一仿真条件，基线是三次决策错一次 |
| `ASC` | 重复工具调用 | 3 → 0 | 同参数同工具的重复次数 |
| `ASC` | 跨会话恢复步数 | 2 → 1 | 从中断恢复到完成任务所需步数 |
| `ASC` | 任务完成率 | 100% 持平 | 同一仿真条件，证明不是靠少给信息换来的 |
| `ContextFS` | 每查询注入 `token` | 1002.8 → 128.7（降 87.2%） | 固定语料 + 哈希嵌入下的确定性下限 |
| `ContextFS` | `recall@3` | 1.0 持平 | 召回质量不降 |

这些数不是孤立的。用同一套治理思路做的标书 `Agent`，初稿编制从 3 天压到 4 小时（口径：业务方验收统计）；称重平台查询从数小时到秒级（口径：与人工拉报表的对照）。但这两条是业务结果，不是严格 `A/B`，我不会把它和仿真数据混着讲。

## 边界：这套东西什么时候不成立

- `Runtime` 七步不是每次调用都要走全：内部只读、无副作用、单租户的工具，走全套是纯开销。
- `MCP` 在只有一个 `Host`、工具又少的时候不如直连，协议的价值在复用，不在整洁。
- 安全那几层收敛解决的是身份、体积、版本，解决不了模型自己编参数——那属于上一篇讲过的错误分类范畴。
- 评估最容易骗自己：仿真只是下限；小样本上的微小差异大概率是噪声；评测集会过拟合，得把真实 `bad case` 定期回补进去。

下一篇我想把这套评估搬到真实模型上：同一批场景、温度固定、每场景 `N ≥ 5`，看仿真里的收益在端到端打几折。

这套东西在你那儿大概率不成立的地方是**只有一个 `Host`、工具又少时，协议层反而是负担**，欢迎说说你的场景。
