今日学习计划：这一篇接着上一篇（上）往下走，不重复调用流程、幂等、错误处理和 `Tool Registry` 契约，只补四块缺口——把每次调用变成可观测、可控制、可追责的 `Tool Runtime`，让多个宿主复用同一批能力的 `MCP`，调用链上的安全边界，以及能证明"改完有没有变好"的评测。我当时想的是：把声明层讲清楚就够了；真到第二个业务系统接进来才发现，声明只是入口，入口之后那段路径没人管。

我 2024 年初转 AI，从 0 组建并带起 10 人左右的研发团队（后端 / 数据 / 前端 / 测试），先后交付的公司级 AI 项目（标书生成、称重问答）共用一套底座；出来后把工具治理那层抽成开源组件。越往后越确认一件事：**`Tool Registry` 只回答"有哪些工具、参数长什么样"，真正决定线上会不会出事的，是声明之后的那段执行路径。** 上一篇我把声明讲完了，这一篇讲声明之后。

# Tool Runtime

## 执行层要的是"三可"

模型输出的 `tool_calls` 只是调用意图，不是执行；真正执行永远在你的代码里。这句话上一篇讲过，这里不重复。我要补的是另一半：当工具有十几个、调用有副作用、还要按租户分权时，怎么让每一次调用都**可观测、可控制、可追责**。

我最早把校验和鉴权散在各个业务函数里，每个工具自己写一遍。结果三个现象：同一个 `requiredScopes` 在 A 工具里校验、在 B 工具里漏掉；一个慢接口把整条会话拖住；出了问题查不到"当时谁调的、传了什么"。我当时想的是"每个工具自己管自己更灵活"，这一步我错了——灵活换来的是不一致和不可追责。

最后的做法是收敛到一个 `Tool Runtime`：所有调用走同一段路径，路径上设七个检查点，顺序不能乱。

```
1 白名单：这个 Agent 能调这个工具吗
2 参数校验：JSON Schema + 业务规则
3 鉴权：租户 / 角色 / 数据范围
4 幂等：幂等键是否已执行（细节见上一篇）
5 执行：超时 / 重试 / 限流
6 结果裁剪：截断 / 结构化 / 脱敏
7 审计：输入输出、耗时、token
```

七步里，白名单、`JSON Schema` 参数校验和 `requiredScopes` 鉴权决定"能不能调"；幂等和错误分类决定"失败了怎么办"，这两块上一篇已经展开，这里只把它们放回执行层的位置，不再讲细节。真正属于 `Runtime` 自己的，是执行、结果裁剪和审计。

**结果裁剪是最容易被忽略的一环。** 我在标书项目里踩过：一个订单查询返回 200 条 `JSON`（单个列表接口的原始返回量），全量回填之后上下文被撑爆，后续推理质量跟着崩。三种裁法我都在用：列表类截断，保留前 N 条加"还有 X 条"；结构化数据只保留模型判断需要的字段；长文本先用小模型摘要再回填。原则是**回填给模型的是它做判断需要的最小集，不是原始数据**。

执行这一环我加了限流和超时，并把审计做成强制：每次调用记录 `traceId`、`name`、参数、结果和耗时。**可追责不是事后能翻日志，而是每次调用在发生之前就决定要留下什么。** 这也是我后来把 `Tool Runtime` 从"一个 `helper` 函数"升级成"一层"的原因。

# MCP

## 组合爆炸与三个角色

`MCP` 解决的不是传输，是组合爆炸：M 个模型 × N 个工具本来要写 M×N 套适配，有了 `MCP` 变成 M+N。我第一次接 `IDE` 宿主时就是吃了没有统一协议的亏——每接一个宿主就把工具适配重写一遍。

`MCP` 有三个角色：`Host` 是宿主应用，管理连接、决定暴露哪些能力、做权限与确认；`Client` 是 `Host` 内部的连接器，与某个 `Server` 一对一通信；`Server` 是能力提供方，也就是你的业务系统。**`Host` 管"给模型看什么"，`Server` 管"提供什么能力"，`Client` 管"怎么把两边接起来"。** 分清这三层，才知道鉴权该放在哪一侧。

我自己那份 `MCP Server` 现在对外 15 个工具（原版 11 个 + 端到端测试新增 4 个），就是按这个模型把 `Tool Registry` 里的工具批量适配成 `Tools`，额外暴露 `Resources`（`状态卡`）和 `Prompts`（常用分析模板）。

## 三类能力、传输与治理点

三类能力我按一句话记：**`Tools` 是"做"，`Resources` 是"看"，`Prompts` 是"问的模板"。** `Tools` 由模型决定调用、可以有副作用；`Resources` 是只读数据，由应用或用户选择挂载；`Prompts` 是预置模板，由用户显式选择。分清楚这三类，才知道哪些要幂等、哪些要控体积。

传输上，本地用 `stdio`，由 `Host` 拉起 `Server` 子进程；远程那套原来走 `HTTP + SSE`，现在主流已经迁到 `Streamable HTTP`（请求响应 + 可选流式）。生命周期是 `initialize` 交换协议版本与 `capability`，`initialized` 通知，然后正常调用。**能力协商是关键：双方各自声明支持什么，不支持的功能不能假定存在。**

治理点有四条，是"读过文档"和"做过"的分界线：工具 `description` 要写"什么时候不用"；`Server` 侧必须自己做鉴权；返回体积要控；协议升级要兼容旧 `Client`。后两条属于安全和边界，放到下一节展开。

# 安全

## 鉴权、越权与返回体积

`MCP` 不解决安全，这一层得自己做。第一个坑是盲信 `Host` 传来的身份：`Host` 说这个用户是谁你就当真，等于把越权入口敞开。我的做法是 `Server` 侧独立校验 token 与租户，再按 `requiredScopes` 做数据范围检查；跨租户访问统一返回 `404`（不暴露资源是否存在）。**鉴权必须在能力提供方自己完成，不能指望上游替你把关。**

第二个坑是返回体积。`MCP` 没有强制的返回上限，一个 `resource` 返回 5MB（单个资源对象的原始体积）就能直接打死上下文。我把上一节的结果裁剪搬到这里：列表截断、字段裁剪、小模型摘要三选一，只回填做判断需要的最小集。**体积控制不是性能优化，是安全问题——上下文被撑爆之后，任何 `硬约束` 都可能被稀释。**

第三个坑是版本。`Tool Registry` 里我给 `name` 用 `name@version` 双写，保留旧版本一个协议周期；`initialize` 阶段做 `capability` 协商，老 `Client` 不支持的能力不假定存在。**升级时兼容旧端，比升级本身更重要**——否则一次协议升级就让一批用户集体连不上。

# 评估

前面三节讲的是"怎么做"，这一节讲"怎么知道做对了"。**不能评测的优化都是猜测，"感觉变好了"在工程上等于没做。** 我在标书项目里把初稿编制从 3 天压到 4 小时（同一套流程、同一验收口径）、合规问题提前发现率约 70%（覆盖保证金 / 签字盖章等检查点），称重平台把人工拉报表的数小时查询压到秒级（同一批统计口径）；这些数字能拿出来讲，靠的是下面这套方法。

这几个数字不是一次试出来的。我最早拿几个 `case` 手测，改一版跑三个（我自己挑的样本），觉得好了就上线；后来发现我挑的 `case` 都是我会的，真实用户的问题一定比我挑的怪。我也试过只看最终答案对不对，结果同一个工具用相同参数调了三次（同一轮内）、`token` 悄悄翻倍这种事全被漏掉。最反直觉的一次是直接用真实模型做回归：同样输入两次结果不同，分数变了根本分不清是方案生效还是模型随机波动；跑一轮几百次调用还要等，人就不想改了。

方法上守唯一变量：锁死模型版本（不用 `latest`）、`temperature=0`、同一批样本、同一个判分器；对照用 `A/B` 和 `A/B/C`，再加 `消融`回答"哪个机制真正起作用"；每个场景重复 N≥5 次（N 为单场景重复次数下限），报均值和方差，不报单次。

## 两把尺子

第一把尺子是 `ASC`。它做的是运行时状态治理，用确定性 `MockAgent` 仿真隔离模型变量（把模型换成规则决策器，两次运行唯一差异只剩注入了什么上下文）。在这一口径下：每轮输入 `token` 从 161 降到 47（降 70.8%）；关键约束违反率从 33.3%（每三次决策一次违反）降到 0；重复工具调用从 3 次降到 0 次；跨会话恢复重放步数从 2 步降到 1 步；两组任务完成率都是 100%，持平。我还加了一组 `无限窗口对照`（不裁剪、换更长窗口的模型），`token` 仍从 147 降到 47（降 68.0%），排除了"只是截断了历史"这个解释。**完成率持平这一条最重要——省 `token` 最容易的做法是少给信息，但那会掉正确率；完成率不变而 `token` 大降，才说明是提效而不是偷工减料。**

第二把尺子是 `ContextFS`。它是上下文按需加载，用固定语料 + 哈希嵌入做确定性下限验证（排除嵌入随机性）：每查询注入 `token` 128.7 对 1002.8（降 87.2%），`recall@3` 为 1.0，召回质量不降。**这两组数字都是注入层的收益，不是端到端收益**——口径必须写清，否则被问一句"真实模型下呢"就站不住。

## 边界

这套东西有几处不成立：`MockAgent` 仿真只是下限验证，它证明机制在原理上有效，不证明在真实模型上也有效；短任务（几轮就结束）加一层状态编译是纯开销；语料没有层级时，`ContextFS` 那种分树按需加载也是白费力气；`MCP` 在只有一个宿主、工具又不多的场景里，统一协议带来的复用收益盖不过接入成本。还有一条最容易被自己骗：**评测集会过拟合，一周不更新就开始给假的好消息，真实 `bad case` 要不断回补。**

下一篇我回到评测那条线，具体写怎么用确定性仿真给这些数字背书。这套东西在你那儿大概率不成立的地方是 `MCP` 在单宿主、少工具的场景里根本用不上，欢迎说说你的场景。
