今日学习计划：上一篇《Agent Day2：Tool Use 学习（上）》把调用流程、幂等、错误处理与 `Tool Registry` 那套结构讲完了，这一篇往下再走一层。我这两天一直在想同一个问题：模型说"我要调这个工具"之后，**凭什么你敢让它真的执行**。今天要解决的就是 `Tool Runtime`、`MCP`、安全、评估这四件事——不是把上篇的流程再背一遍，而是回答一个我被问过很多次的问题：工具这层，怎么做到可观测、可控制、可追责，以及我怎么知道它改完确实变好了。

# Tool Runtime

模型输出的 `tool_calls` 只是调用意图，真正的执行永远发生在你自己的代码里。这句上篇说过，这里不重复。我今天想讲的是意图之后那个执行层：它要把一次调用，变成一次可观测、可控制、可追责的操作。

我当时想的是，这不就是一次简单分发吗。真正上手才发现要管的有七件事，顺序还不能乱：白名单、参数校验、鉴权、幂等、执行、结果裁剪、审计。幂等键和错误分类上篇已经拆过，这里只说它们在这一串里的位置——它们夹在鉴权与执行之间，是执行前最后两道闸。

**参数校验必须双层。** 我踩过一次坑：只在 `schema` 层校验类型，结果把字符串 `"30"` 当日期传进下游，接口直接炸。后来改成 `schema` 管类型、业务规则管语义，这类问题才没了。工具契约里最好把 `requiredScopes` 也写进去，鉴权时直接读，不用临到调用再去翻配置。

**结果裁剪是最容易被忽略的一环。** 我之前一个查询一次返回 200 条 `JSON`（口径：一个订单列表接口的实际返回），整段回填进上下文，后面的推理全乱了。三种裁法我都用过：列表类只留前 N 条加"还有 X 条"；结构化数据只留模型做判断要用的字段；长文本先让小模型摘要再回填。原则就一句——**回填给模型的是它做判断需要的最小集，不是原始数据。**

审计这块，我最早只记成功调用，出事以后查不到谁调的、传了什么。现在输入输出、耗时、`token` 全记，带 `traceId` 能串起整条链。执行这一档还要兜住超时、重试、限流、熔断，不然一个慢接口能拖死整个会话。

最后的做法是把 `Tool Runtime` 做成唯一收口点：任何工具调用都必须过这一层，业务代码不许直接调工具，控制面才立得住。边界也明显——三五轮、无副作用、单人用的短任务，加这层是纯开销；但只要有多人协作、有副作用、要事后追责，它就值。

# MCP

单个 Agent 接几个工具时，直连没问题；一旦是多个模型对多个系统，就会撞上组合爆炸——M 个模型 × N 个工具，要写 M×N 套适配。`MCP` 把它变成 M+N，这是它存在的理由。

它有三个角色：`Host` 是宿主应用，管连接、决定哪些能力暴露给模型、做权限与确认；`Client` 是 `Host` 内部的连接器，和某个 `Server` 一对一通信；`Server` 是能力提供方，也就是你的业务系统。三类能力要分清：`Tools` 是"做"，模型决定调用，有副作用；`Resources` 是"看"，只读数据像文件，由应用或用户挂载；`Prompts` 是"问的模板"，用户显式选择。我记它的方式是：**做、看、问的模板。**

传输上有三种：`stdio` 走本地进程，最简单；`HTTP + SSE` 是旧方案，Server 到 Client 单向流；`Streamable HTTP` 是新的，请求响应加可选流式，正在逐步替代 SSE。生命周期是 `initialize` 交换协议版本与能力、`initialized` 通知、正常调用、关闭。**能力协商是关键：双方各自声明支持什么，不支持的不能假定存在。**

真正区分"做过"和"读过文档"的，是四个治理点：工具描述同样要写"什么时候不用"，否则模型乱调；`Server` 侧必须自己鉴权，不能盲信 `Host` 传来的身份；返回体积要控，`MCP` 没有强制大小限制；版本升级要兼容旧 client。顺便更正一个我自己的旧数据——早先那版是 11 个工具，按当前 ASC 对外 `MCP Server` 的实际清单，是 15 个：原版 11 个，加端到端测试新增的 4 个（口径：仓库里实际的对外工具清单）。

边界要说清：`MCP` 是能力描述协议，不是银弹。它不替你做鉴权和体积控制，也不管超时重试，这些还是得在 `Server` 侧自己做。

# 安全

工具有了副作用之后，"能调"和"该不该调"是两回事。我把安全拆成鉴权、越权、返回体积、版本协商四块。

鉴权上，我有一条硬规矩：`Server` 侧独立校验 token 与租户，不能盲信上游传来的身份。多租户用 `X-ASC-Tenant` 分区，跨租户统一返回 404 防探测（口径：这是我在 ASC 里的实现）。越权靠三层收口——白名单、租户与角色、数据范围；每把工具的 `requiredScopes` 写在契约里，鉴权时直接读。

返回体积看着是性能问题，其实是安全问题。一个 5MB 的 `resource` 就能把上下文打死，而 `MCP` 不拦这个，所以结果裁剪要前移到协议出口。还有一条我踩过的坑：别把异常堆栈整段回填给模型，它会开始"解释"报错、越跑越偏；只回填可执行的错误摘要就行——错误分类上篇讲过，这里不展开。

版本协商这块，工具 `schema` 一改，老 Agent 可能直接崩。我的做法是 `name@version` 双写，旧版本保留一个周期；协议升级靠 `initialize` 的能力协商兜底，别让老 client 集体连不上。

边界在哪：鉴权做在 `Server` 侧，会带来每个 Server 的重复建设，集中式网关能缓解但引入单点。**安全没有配一次就完的事，它跟着工具数量和租户数量一起长。**

# 评估

"改完感觉好了"这句话，在工程上等于没做。Agent 评测难在四个地方：非确定性、变量太多、没有唯一答案、链路太长。核心问题只有一个——怎么在这么多变量里，只让一个动。

我试过的错有三个。一是手测几个 case，最大的问题是过拟合到自己：那几个 case 是我挑的，我甚至隐约知道怎么问它才能答对。二是只看最终答案对不对，可 Agent 的失败常在过程里——同一个工具相同参数调三次、`token` 悄悄翻倍、走十几步才到本来几步就能到的地方，只看答案这些全看不见。三是直接拿真实模型跑回归，不可复现、又贵又慢，跑一轮几百次调用，迭代一次等半天，人就不想改了。

最后的做法，先用 `MockAgent` 规则决策器把模型按住，再上真实模型验一次。这样任何分数变化都只能来自我改的那一层，因果链才清楚。配套几条规矩：锁模型版本、温度 0、同一批样本、同一个判分器；除了 `baseline` 再加一组无限窗口对照当上界，再加消融看每个机制的真实贡献；每场景重复 N≥5、场景数 20 个以上，报均值和方差；规则类指标占 70% 以上，要用 `LLM-as-judge` 就先拿 50 条人工标注校准。

数字我给带口径的。ASC 的确定性仿真（口径：用 `MockAgent` 规则决策器隔离模型变量，组间唯一差异是注入内容，场景 3 个）：每轮输入 `token` 161 → 47（−70.8%），关键约束违反率 33.3% → 0，重复工具调用 3 → 0，跨会话恢复步数 2 → 1，两组任务完成率都是 100%。这里 33.3% 就是三次里错一次，样本只有 3 个场景，**不足以支撑统计结论，我主动说在前面**。无限窗口对照下 `token` 仍从 147 降到 47（−68.0%），排除了"只是截断历史"这个解释。ContextFS 那组：同一命中集合下注入 `token` 128.7 对 1002.8（−87.2%），`recall@3` = 1.0，口径是固定语料加哈希嵌入的确定性下限，不是真实模型下的绝对值。

边界必须主动说：**仿真只是下限验证**——它能证明机制在原理上有效，不能证明在真实模型上也有效。真实 `LLM` 的端到端评测在 `v0.7` 做，同模型、温度 0、结构化决策输出、规则化判分、每场景 N≥5。另外评测集会过拟合，我每周把真实 bad case 回补进去，不然它就只会给我假的好消息。

这套东西在你那儿大概率不成立的地方是工具少、调用没有副作用、也没有多人交接的短链路场景，欢迎说说你的场景。下一篇我想把话题往回拉一层：模型到底是怎么"想"出那些 `tool_calls` 的——也就是它生成调用意图的那点事。我们下篇见。
