今日学习计划。上一篇《Agent Day2：Tool Use 学习（上）——调用流程、幂等、错误处理与 Tool Registry 四域架构》把"模型想调什么"到"真的调起来"那条链路讲完了：一次调用的七个环节、`tool_calls` 怎么回填、幂等键怎么算、错误怎么分类。今天接着往下走，解决工具真正放进生产环境之后的四个问题——执行层怎么做到可观测、可控制、可追责；外部工具怎么用一套协议接进来，而不是给每个宿主都重写一遍适配；身份、越权、返回体积这些安全问题在哪一层兜住；以及我自己最在意的一条：改完这套东西，我凭什么说它真的变好了。涉及的关键字我用反引号标出来，重点结论加粗。下面按 `Tool Runtime`、`MCP`、`安全`、`评估` 四块讲。

## Tool Runtime

**问题：执行层不是 `switch` 一下就完了。** 我最早以为，工具治理就是把 Function Calling 的链路跑通、把 `Tool Registry` 注进去。真到标书 Agent 上线，问题全出在执行这一步：一次查询返回 200 条 `JSON`，直接把上下文撑爆，后面整段推理都乱了；一个慢接口能把整个会话拖住；出了事我答不出"当时是谁调的、传了什么、花了多少"。这些都是上一篇没有展开的部分。我当时把每一类问题都单独记了一笔：慢接口拖会话、超大返回撑上下文、事后查不到调用记录——它们都不是模型选错工具，而是执行这一层缺了约束。

**我试过的错：把治理写进提示里。** 我当时想的是，把"别返回太多""注意权限"写进提示词，让模型自己守。结果很直接——模型不执行函数，它只在 `tool_calls` 里输出"调用意图"，真正执行永远发生在我的代码里，写进提示等于把闸门装在了门外。还有一次我把异常堆栈原样回填给模型，它开始一本正经地"解释"报错，越跑越偏。权限判断写在提示里也一样不牢靠，复盘时我根本拿不出证据证明某个用户没被越权放行。

**最后的做法：把七个环节固化成一层。** 我把一次调用固化成 `Tool Runtime` 这一层，按顺序走七步：`白名单`、`参数校验`、`鉴权`、`幂等`、`执行`、`结果裁剪`、`审计`。幂等和错误分类上一篇讲过，这里不重复；真正让这一层立住的是另外几步。`白名单`决定这个 Agent 能调哪些工具；`鉴权`校验租户、角色和数据范围；`执行`处统一收口超时、重试和限流，慢接口在这里被挡住；`结果裁剪`是我踩坑最多的一环——列表类截断、结构化数据只留字段、长文本先用小模型摘要，回填给模型的必须是它做判断需要的最小集，而不是原始数据；`审计`把输入输出、耗时、`token` 一条条记下来，出事能按 `traceId` 回放。**这一层的价值不是"能调工具"，而是把一次调用变成可观测、可控制、可追责的操作。**

## MCP

**问题：M 个模型 × N 个工具。** 工具接多了，最烦的不是写工具，是适配。M 个模型对 N 个工具，不治理就是 M×N 套适配。`MCP`（Model Context Protocol）把它变成 M+N：工具按一套标准描述一遍，谁都能接。

**三个角色、三类能力。** `MCP` 里就三个角色：`Host` 是宿主应用，管连接、决定暴露哪些能力、做权限和确认；`Client` 是宿主内部的连接器，跟某个 `Server` 一对一通信；`Server` 是能力提供方，也就是我的业务系统。能力分三类：`Tools` 是"做"，有副作用、由模型决定调用；`Resources` 是"看"，只读数据、由应用或用户选择挂载；`Prompts` 是"问的模板"，由用户显式选择。记法是——`Tools` 做、`Resources` 看、`Prompts` 问。传输上，本地用 `stdio`，远程从 `HTTP + SSE` 逐步迁到 `Streamable HTTP`。生命周期是 `initialize` 交换协议版本与能力、`initialized` 通知、正常调用、最后关闭；能力协商这一步很关键，双方只声明自己支持什么，不支持的不能假定存在。

**我的实践：15 个工具与四个治理点。** ASC 的 `MCP Server` 现在对外 15 个工具，口径是原版 11 个加上端到端测试新增的 4 个。把 `Registry` 里的工具批量适配成 `MCP` 的 `tools` 列表，再额外暴露 resources（状态卡）和 prompts（分析模板），这就是我做的全部工作。迁移传输那阵我踩过一个坑：client 还停在旧传输、server 已经切到新传输，结果用户端集体连不上，最后靠能力协商和双写才平滑过去。但协议本身不管治理，有四个点必须自己在 `Server` 侧补：工具描述要写"什么时候不用"，否则模型乱调；身份不能盲信 `Host` 传过来的，要独立校验 `token` 和租户；返回体积没有强制上限，一个 resource 回 5MB 就直接打死上下文；协议升级要兼容旧 client，否则用户端会集体连不上。**`MCP` 解决的是组合爆炸，不是治理本身——治理那部分还得自己写。**

## 安全

**问题：安全不是一个开关，是运行时的一组约束。** 工具一旦有副作用，安全就不再是"登录一下"那么简单。我把它拆成四件事。

**鉴权与越权。** 第一，鉴权要放在 `Server` 侧独立做。我早期图省事，直接信了 `Host` 传过来的身份，这在多租户场景下等于谁都能调内部系统；正确做法是校验 `token` 与租户，再按角色和数据范围收口，普通用户不该调到管理员工具。第二，越权检查要和参数校验叠在一起做，schema 管类型、业务规则管语义，两层都不能省。

**返回体积与版本协商。** 第三，返回体积。`MCP` 没有强制大小限制，我在运行时给 `结果裁剪` 设了硬上限，列表截断加字段裁剪，避免一次返回把上下文打满。第四，版本与能力协商。工具 schema 一改，老 Agent 可能直接崩；我用 `name@version` 双写，保留旧版本一个周期，配合 `initialize` 阶段的能力协商，让升级不会把用户端一起打断。**这四件事的共同点是：都不能指望模型自觉，必须落在运行时的代码里。**

## 评估

**问题：改完，我凭什么说它变好了。** 这是我最在意的一节。2024 年初我转 AI 方向、从 0 组建起一支 10 人左右的研发团队，最大的体会是：说"优化有效"容易，拿数出来难。我一度反复改提示词、试三个 case 就觉得好了，直到被问"你到底提升了多少"，我答不上来——那几个 case 是我自己挑的，我甚至隐约知道怎么问才能让它答对。

**我试过的错：拿真实模型跑回归。** 真实模型是最大的噪音源。同一个输入两次结果不同，我改了 A、分数变了，根本分不清是 A 起效还是随机波动；而且贵、慢，迭代一次要等很久，人就不想改了。

**最后的做法：用确定性仿真按住变量。** 我用规则决策器替代真实模型做确定性仿真——输入固定、规则固定，两次运行唯一的差异只剩"注入了什么上下文"，因果链一下就清晰了。对照实验守唯一变量：模型版本锁死、温度 0、同一批样本、同一个判分器，每场景重复 `N≥5` 次报均值，不报单次；设计上用 `A/B`、`A/B/C` 加消融，分别回答"有没有变好""离天花板还有多远""哪个机制真起作用"。

**数字与口径。** ASC（确定性仿真、规则决策器隔离模型变量）：每轮输入 `token` 从 161 降到 47，降 70.8%；关键约束违反率 33.3% 到 0；重复调用 3 次到 0；恢复步数 2 步到 1 步；两组任务完成率都是 100%——**完成率持平这一条最重要，它证明省 `token` 不是靠少给信息换来的**。ContextFS（固定语料、哈希嵌入的确定性下限验证）：每查询注入 `token` 128.7 对 1002.8，降 87.2%，`recall@3` 为 1.0，召回不降。这两个数都是注入层的确定性仿真结果，边界必须写清：它们证明了机制在原理上有效，不等于真实模型下的端到端收益；真实 LLM 评测仍在进行，口径是同模型、温度 0、结构化决策输出、规则判分、每场景 `N≥5`。我给自己定的规矩是：任何一个数后面都要能接上"怎么测的、测了多少、什么条件"，接不上就不写进来。

**边界：这套东西什么时候不成立。** `Tool Runtime` 那一层，在工具少、调用无副作用、也不需要多人审计的场景里是纯开销；`MCP` 只在要给多个宿主复用时才值，单个应用直连更简单；仿真的分数不能当端到端成果对外讲，小样本上的差异大概率是噪声。**说得出边界，比声称"我验证过了"更可信。**

这套东西在你那儿大概率不成立的地方是工具少、调用没有副作用、也没人需要审计，欢迎说说你的场景。下一篇我们回到状态层，讲讲 Agent 跑着跑着把前面定下的规则忘了这件事。
