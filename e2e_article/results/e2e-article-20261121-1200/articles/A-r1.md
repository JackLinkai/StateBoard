今日学习计划

上一篇《Agent Day2：Tool Use 学习（上）——调用流程、幂等、错误处理与 Tool Registry 四域架构》发出之后，后台被问得最多的一句是：

> 模型吐出一个 `JSON` 之后呢？谁保证它真的被执行、被正确地执行、执行完还能查到痕迹？

这问题问到了点子上。上篇讲的 `Tool Registry` 只是一份静态契约——它回答"有哪些工具、长什么样"。但从"模型想调"到"真的调了"，中间隔着一整层运行时。今天的学习计划，就围着四个词转：`Tool Runtime`、`MCP`、安全、`评估`。

先交代今天的四个目标，再逐个拆开。

**目标一·`Tool Runtime`：把一次调用变成可观测、可控制、可追责的操作。**

我以前以为执行层就是 `switch(name)` 调一下函数。后来在标书 Agent 里踩了坑才明白，**执行层真正的价值是"每一步都能被拦住"**。一次调用要过七道关：

1. `白名单` 校验——这个 Agent 允许调这个工具吗；
2. `参数校验`——`JSON Schema` 管类型，业务规则管语义，必须双层；
3. `鉴权`——租户、角色、数据范围，一个都不能少；
4. `幂等检查`——有副作用的工具，先看 `幂等键` 在不在；
5. 执行——`超时`、`重试`、`限流`、`熔断` 全在这一层；
6. `结果裁剪`——列表截断、字段裁剪、小模型摘要，三选一；
7. `审计`——输入输出、耗时、`token`，一条不落。

这七步的顺序不是随便排的，**鉴权必须在执行前，审计必须在返回前**。当时我图省事把审计放最后异步写，结果出了一次事故想复盘，发现日志缺了关键三分钟——从那以后我改成先记后返回。

> 一个最容易被忽略的细节：`arguments` 是字符串不是对象，要自己 `JSON.parse`，还得处理模型偶尔吐出来的带尾逗号、带注释的 `JSON`。这个不处理，线上迟早炸。

**目标二·`MCP`：用标准协议解决组合爆炸。**

`M` 个模型 × `N` 个工具，直连就是 `M×N` 套适配。有了 `Model Context Protocol`，变成 `M+N`。它的三个角色要先分清楚：

| 角色 | 是谁 | 干嘛 |
|---|---|---|
| `Host` | 你的 Agent 平台 / IDE | 管连接、决定暴露什么、做确认 |
| `Client` | Host 内部的连接器 | 跟某个 `Server` 一对一通信 |
| `Server` | 能力提供方 | 暴露 `tools` / `resources` / `prompts` |

三类能力的记法我一直用这句：**`Tools` 是"做"，`Resources` 是"看"，`Prompts` 是"问的模板"**。传输上新项目直接用 `Streamable HTTP`，老的 `SSE` 单向流能不用就不用；本地调试用 `stdio` 最省事。生命周期里最关键的是 `initialize` 阶段的 `capability` 协商——**双方没声明的能力，绝不能假定它存在**。

我在 ASC 里把 `Registry` 的 11 个工具批量适配成 `MCP` 的 `tools`，额外挂了 `resources`（状态卡）和 `prompts`（分析模板）。这里有个反直觉的坑：**`MCP` 不负责鉴权，也不限制返回体积**。Host 传来的身份不能盲信，`Server` 侧必须自己校验 token 和租户；一个 `resource` 返回 5MB，能直接把上下文打死。

**目标三·安全：能调、该调、调完查得到。**

安全这一块，我的原则就一条：**控制权在代码里，不在模型里**。模型只输出"调用意图"，真正的闸门全在运行时。落到三件事：

- **权限收敛**：`ToolSpec` 里带 `requiredScopes`，越权直接 `denied`，不解释；
- **错误分类**：`Retryable`（超时、429）退避重试三次，`Permanent`（401、404）立刻失败，`Fixable` 把**可执行的错误**回填给模型让它改参数（最多两次），`HumanRequired` 走 `HITL` 人工；
- **可追溯**：`TraceId` 贯穿全链路，出问题能回答"当时谁调的、传了什么、花了多久"。

最忌讳的是所有错误一律重试——我见过 401 被重试三次，既浪费三倍时间，又把故障放大。`sealed interface` 把错误类型封闭起来，编译期穷尽检查，这类错就很难漏。

**目标四·`评估`：不能评测的优化都是猜测。**

"我改了工具描述，选择准确率高了"——这句话在面试里等于没说。要证明有效，三件事：

1. **隔离变量**：用 `MockAgent` 规则决策器替代真实模型，锁定模型版本、固定 `temperature=0`、同一批样本，让两次运行唯一的差异只剩"被测那一层"；
2. **看过程指标**：不止看任务完成率，还要看 `约束违反率`、`重复调用率`、每轮输入 `token`、恢复步数；
3. **加对照**：除了 `Baseline`，再加一组"无限窗口"对照，排除干扰解释。

我在 ASC 上跑的确定性仿真，数字可以拿出来讲口径：

| 指标 | Baseline | 优化后 | 变化 |
|---|---|---|---|
| 每轮输入 `token` | 161 | 47 | **−70.8%** |
| 关键约束违反率 | 33.3% | 0 | **−100%** |
| 重复工具调用 | 3 | 0 | **−100%** |
| 恢复重放步数 | 2 | 1 | **−50%** |

口径必须写清：**这是确定性仿真（`MockAgent` 隔离模型变量）的结果，不是端到端收益**。真实 LLM 端到端评测（`v0.7`：同模型、`temperature=0`、结构化决策输出、规则化判分、每场景 `N≥5`）还在进行中。另外任务完成率两组都是 100%——**省 token 不是靠少给信息，这一点必须主动讲**。工具侧同理：我会在离线集上固定 50 条 query 看工具选择准确率，改完描述跑一遍对比，不靠感觉。

**写在最后：这套东西的边界。**

`Tool Runtime` 的七步不是每个项目都要全上——内部小工具、调用量小、无副作用时，做全套是过度工程。`MCP` 只有在需要给多个 Host 复用时才划算，单个应用直连 `HTTP` 更简单。评测集一周不回补真实 bad case，就开始给你假的好消息。**仿真测出来的是下限，不是承诺**——真实模型下一定要打折看，我自己预期打七折。

明天继续往下走：把今天这四个目标落到代码，用一次真实的工具调用把七步链路跑通，再拿评测集验一遍。

这套东西在你那儿大概率不成立的地方是工具少、没有副作用、也没人要复用，欢迎说说你的场景。
