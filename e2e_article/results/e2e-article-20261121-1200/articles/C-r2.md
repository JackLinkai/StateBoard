今日学习计划：接着上一篇《Agent Day2：Tool Use 学习（上）》往下走。上一篇把调用流程、幂等、错误分类和 Tool Registry 四域架构讲透了，我当时停在一个问题上——声明得再清楚的工具，真正被调用的那一刻，到底由谁看着。今天这篇补上剩下的四块：`Tool Runtime`、`MCP`、安全、评估。目标很具体：把这层"模型想调什么"和"真的能调"之间的运行时看清楚，再用可复现的数证明它有效，而不是靠一句"感觉变好了"。

## Tool Runtime

**模型不执行函数，它只输出调用意图。真正执行永远发生在你的代码里**，这是我理解 Runtime 的起点，也是三条主线里"控制权要在代码里"落到工具上的样子。

最早我把工具当普通函数处理：拿到 `tool_calls`，按名字分发一下就调。当时我想的是"能把结果回填给模型就行"。很快问题一起冒出来：普通租户能调到管理员工具；一个慢接口把整条会话拖死；一个订单查询返回 **200 条** `JSON`，全量回填直接把上下文撑爆，后面的推理全乱；真出了事，我答不上来"当时是谁调的、传了什么、花了多久"。

后来我把 Runtime 定位成一层**可观测、可控制、可追责**的执行层，一次调用按顺序过七个环节：白名单、参数校验、鉴权、幂等检查、执行、结果裁剪、审计。幂等和错误分类上一篇已经讲过，这里不重复，今天重点看另外几步。

**白名单**先回答"这个 Agent 允许调哪些工具"，不在清单里直接拒绝，不靠模型自觉。**参数校验**要双层：`JSON Schema` 管类型，业务规则管语义，缺一层都会让 `"30"` 这种值流到下游。**鉴权**校验租户、角色和数据范围，不是只看"登没登录"。**执行**把超时、限流、熔断包在外面，一个慢接口不能拖死整条会话。**审计**把输入输出、耗时、`token` 用 `traceId` 串起来，出事能按链路回放，这才叫可追责。

**结果裁剪是最容易被忽略的一环。** 我踩过的那个坑——一次查询返回 **200 条** `JSON` 撑爆上下文——根因就是没裁。三种裁法我都在用：列表类**截断**，保留前 N 条加"还有 X 条"；结构化数据**只保留模型需要的字段**；长文本先用小模型**摘要**再回填。原则一句话：**回填给模型的是它做判断需要的最小集，不是原始数据。** 这一层做不好，后面省 token 的优化都是空谈。

七个环节的顺序也不是随便排的：先确认"能不能调"（白名单、鉴权），再确认"参数对不对"，然后才轮到"要不要真的执行"（幂等、执行），最后才是"怎么把结果安全送回去"（裁剪、审计）。我一开始把鉴权放在参数校验之后，结果一个非法参数就能绕过权限去探测内部工具——这是把顺序放错要付的代价。

## MCP

`MCP`（`Model Context Protocol`）解决的是组合爆炸：M 个模型 × N 个工具 = M×N 套适配，有了它变成 M+N。

我最早给每个宿主应用写一套适配，改一次工具描述要改好几处，漏一处就在线上出问题。当时我想的是"接口能通就行"，没意识到真正该被标准化的是"能力描述"本身——`HTTP` 只是传输，`MCP` 是让工具是什么、参数是什么、有哪些资源和预设提示变成可复用的契约。

它拆成三个角色：`Host`（宿主应用，管连接、决定暴露哪些能力、做权限与确认）、`Client`（`Host` 内部的连接器，与某个 `Server` 一对一）、`Server`（能力提供方）。三类能力必须分清：

| 能力 | 语义 | 谁触发 |
|---|---|---|
| `Tools` | 可执行的动作，有副作用 | 模型决定调用 |
| `Resources` | 只读数据，像文件 | 应用/用户选择挂载 |
| `Prompts` | 预置提示模板 | 用户显式选择 |

记法很简单：`Tools` 是"做"，`Resources` 是"看"，`Prompts` 是"问的模板"。

为什么值得为它单独写一篇？因为能力一旦标准化，同一个 `Server` 就能被多个宿主复用，不必每个宿主重述一遍工具清单；也不必把资源和提示模板塞进每次请求，让 `token` 随工具数量线性上涨。**协议的价值不在"能连上"，在"能复用且可协商"。**

传输上，本地用 `stdio`，`Host` 拉起 `Server` 子进程最简单；远程从 `HTTP + SSE` 迁到 `Streamable HTTP`。生命周期是 `initialize`（交换协议版本与 capability）→ `initialized` 通知 → 正常调用 → 关闭。**能力协商是关键：双方各自声明支持什么，不支持的功能不能假定存在**，否则升级一侧就会把另一侧打挂。

数字带上口径：`ASC` 当前的 `MCP Server` 对外 **15 个**工具，口径是原版 **11 个**加端到端测试新增 **4 个**——不是一开始就这么多，是随测试逐步加的。

`MCP` 也有四个治理点，这是"做过"和"读过文档"的分界线：描述要写"何时不用"；`Server` 侧必须自己做鉴权；返回体积要控；版本升级要兼容旧 `Client`，否则用户端会集体连不上。

## 安全

安全这一节我拆成四件事：鉴权、越权、返回体积、版本协商。

`MCP` 是能力描述协议，**它不替你做鉴权和体积控制**，这两件永远得自己在 `Server` 侧做。我犯过的错是**盲信 `Host` 传过来的身份**——觉得既然接了标准协议，身份就自带可信。后来改成 `Server` 侧独立校验 `token` 与租户，并且做数据范围校验；跨租户访问统一返回 **404**，防止探测。越权往往不是"没登录"，而是"登录了但看到了不该看的"，所以数据范围这一层比登录态更关键。

这一层我做成显式契约：每个工具声明自己需要的 `requiredScopes`，调用进来先比对租户、角色、数据范围三者，缺一项就拒绝，而不是等执行到下游再报错。好处是拒绝发生在最便宜的地方，**越权不会走到真正有副作用的那一侧**；代价是工具定义要多写几行声明，但比起出事后再补，这笔账划算。

**返回体积是一种安全边界，不只是性能问题。** 一个 `resource` 返回 **5MB** 级别的数据，不是"慢一点"，是直接把上下文打死。所以我在 `Server` 侧设了硬限制，而不是指望调用方克制——这跟 Runtime 里的结果裁剪是同一件事，只是位置挪到了协议边界上。

版本协商上，**升级协议版本时不兼容旧 `Client`，用户端会集体连不上**——这不是"新功能上线"，是"老用户断供"。我把这条当成发布前的必查项：先确认旧客户端还能握手，再谈新能力。

## 评估

改完到底有没有变好？我以前答不上来。有一段时间我陷在循环里：改一版，试三个 case，觉得好了；过两天用户又报错，再改。老板问我"到底提升了多少"，我手里那几个 case 是我自己挑的，我甚至隐约知道怎么问才能让它答对。**没有评测集的优化，本质是在用你的记忆做回归测试。**

我试过的三个错：**拿几个 case 手测**，过拟合到自己，真实用户的问题一定比挑出来的怪；**只看最终答案对不对**，看不见过程里的重复调用、`token` 翻倍、走了 **12 步**才到 **3 步**能到的地方；**直接用真实模型跑回归**，不可复现、贵且慢，改一次等半天，人就不想改了。

最后的做法是**先用确定性仿真定住变量，再上真实模型校一次**。唯一变量原则：模型版本写死不用 `latest`、`temperature=0`、同一批样本同一顺序、同一个判分器、同机器同超时。判分器自己要先被人工标注校准，否则指标全错还浑然不知。对照设计用 `A/B/C` 加消融（`Ablation`），消融最能看出哪个机制真正起作用。每场景重复 **N≥5** 次报均值和方差，场景数 **≥20**，不报单次。

仿真这一层我用 `MockAgent`（规则决策器）替代真实模型，把最大的噪音源按住，两次运行的唯一差异只剩"注入了什么上下文"，因果链才清晰。

数字都带口径：

- `ASC`，口径是**确定性 `MockAgent` 仿真、隔离模型变量**：每轮输入 `token` **161 → 47（−70.8%）**；关键约束违反率 **33.3% → 0**；重复工具调用 **3 → 0**；跨会话恢复步数 **2 → 1**；两组任务完成率均 **100%**（持平，证明不是靠少给信息换来的）。
- `ASC` 无限窗口对照，口径是**不裁剪、全量给但换更长窗口模型**：`token` 仍 **147 → 47（−68.0%）**，排除了"只是截断了历史"这个解释。
- `ContextFS`，口径是**固定语料 + 哈希嵌入的确定性下限验证**：注入 `token` **128.7 vs 1002.8（−87.2%）**，`recall@3 = 1.0`（持平）。

**这些是注入层的下限收益，不是真实模型下的端到端收益**，这句必须写清楚。真实 `LLM` 端到端评测在进行中（同模型、`temperature=0`、结构化决策输出、规则判分、每场景 `N≥5`），仿真里打满分的方案，真模型下大概要打个折看。

还有一条我后来才加的护栏：**完成率必须和成本一起报**。只看 `token` 降了多少没有意义——少给信息谁都会，难的是 `token` 降了、完成率还持平。所以我在表里永远把"完成率持平"和 `token` 数摆在一起，谁想拿这组数去说"端到端提升"，我自己先把边界讲在前面。

### 边界：什么时候这套东西不成立

- **短任务不需要**：三五轮就结束，状态还没开始漂，加一层编译和治理是纯开销。
- **没有副作用、没有多租户时，这层可以很薄**：全是只读查询，幂等和强鉴权的收益很低。
- **单靠协议不会自动安全**：`MCP` 不替你做鉴权和体积控制，那两件永远在你自己的 `Server` 侧。
- **仿真的分数不能对客户讲**：把注入层效果说成端到端提升，就是骗人。

下一篇我打算把评测这一节单独拉开写——怎么用假 Agent 定住变量，再上真模型校准，顺便聊聊仿真分数该怎么打折看。这套东西在你那儿大概率不成立的地方是你的工具全是只读、没有并发也没有交接，欢迎说说你的场景。
